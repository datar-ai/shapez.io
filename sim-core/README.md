# sim-core — 無畫面模擬核心原型

路線圖第 1–3 週的驗證原型：只有輸送帶（模型 B）和一種機器，全整數、決定性、事件驅動，
獨立成一個 Rust 函式庫（沒有任何繪圖或引擎相依）。目標是回答一個問題：
**單執行緒能不能在 10⁷ 個建築下跑到 60 步/秒？**

## 怎麼跑

```
cargo test                                  # 決定性與守恆測試
cargo build --release
./target/release/bench steady  10000000 600 # 穩態滿載（最壞情況之一）
./target/release/bench churn   10000000 600 # 全廠同時堵住 / 同時解除
./target/release/bench jam     10000000 600 # 全廠堵死（驗證休眠成本為零）
```

## 量測結果

機器：4 核心容器、15 GB RAM（不是玩家等級的桌機，單執行緒數字仍可參考）。
場景：526,315 條生產線 × 19 個建築（source → 8 條帶 → 機器 → 8 條帶 → sink），
每條帶 16 格、每 30 tick 前進一格（= shapez 的 2 物品/秒、60 步/秒）。
穩態時輸送帶 94% 滿，帶上有 **1.26 億個物品**。

| 場景 | 建築數 | ticks/秒 | 相對 60 步/秒 | 事件/秒 | 每事件 | 核心記憶體 |
|---|---|---|---|---|---|---|
| 穩態滿載 | 10⁷ | 47–50 | **0.8x** | 1.5×10⁷ | 63 ns | 0.44 GB |
| 全廠劇烈變動 | 10⁷ | 58 | 0.97x | 1.6×10⁷ | 61 ns | 0.44 GB |
| 全廠堵死 | 10⁷ | （無事件） | — | 0 | — | 0.44 GB |
| 穩態滿載 | 10⁶ | 971 | 16x | 3.1×10⁷ | 33 ns | 0.04 GB |

結論：單執行緒在最壞情況下是目標的 0.8 倍，差距落在「多核心」和「降低模擬頻率」這兩個
還沒用到的槓桿裡（第 4–6 週）。10⁸ 個物品這一項已經達標而且幾乎免費。

## 資料結構

每個建築 44 bytes（含 RLE 區段），10⁷ 個建築 = 0.44 GB。

```
Belt    36 B  out, run_head, run_tail, last_tick, link, wait_head, cap, period, gap0, used, flags
Run     12 B  next, item, count, gap          <- RLE 區段，滿載的輸送帶只有 1 筆
Machine 28 B  out, until, link, wait_head, in_item, out_item, dur, need, have, flags
```

幾個關鍵決定：

- **AoS 而不是 SoA。** 事件驅動的存取是隨機的，一個事件要讀同一個建築的十幾個欄位；
  拆成十幾個陣列就是十幾次 cache miss。把「一個事件會碰到的欄位」打包進 36 bytes 才對。
  SoA 仍然適用於之後要做全掃描的地方（繪圖上傳、存檔）。
- **`link` 一個欄位兩用。** 一個節點不可能同時在 timing wheel 和等待串列裡（被堵住的節點
  沒有計時器），所以兩個串列共用同一個指標欄位。
- **格（cell）= 物品間距。** 輸送帶長度以格計，所以「前進一格」就是整數加一，沒有定點小數。

## 輸送帶：模型 B + 懶惰結算

輸送帶內容是從頭端數過來的 RLE 區段串列 `(item, count, gap)`，再加兩個整數
`gap0`（頭端到第一個物品的空格數）和 `used`（最後一個物品的位置 +1）。

- **移動完全不寫資料。** 平常每個 tick 一個 byte 都不用碰；真正要讀狀態時才用
  `(now - last_tick) / period` 把經過的格數一次結算進 `gap0`。這就是「環形緩衝區只加一個偏移」
  的懶惰版本，而且天生支援大量休眠的輸送帶。
- **堵住時整條停住**（目前的預設規則）。物品相對位置固定，所以區段資料在移動時永遠不用改寫。
- **尾端塞入**：如果跟最後一個區段同種物品又緊貼著，就 `count += 1`；滿載的輸送帶因此
  只有 1 筆區段，1.26 億個物品實際上只有幾百萬筆資料。
- 區段帶著物品種類，所以混合物品的輸送帶不用改結構，只是區段數會變多。

## 事件驅動與休眠

- Timing wheel：65536 個 slot 的侵入式串列，超過範圍的丟進 overflow heap（實務上很少用到）。
- 輸送帶只在「頭端物品抵達」時被叫醒，時間直接算出來：`last_tick + gap0 × period`。
- 機器只在「加工完成」時被叫醒。
- 推不進下游時分兩種情況：下游只是滿了但還在跑 → 直接排在它下一次前進的 tick；
  下游整個堵住 → 掛到它的等待串列上睡著，它一有進展就把等待者叫醒。
- 結果：全廠堵死時事件數是 **0**，完全不耗 CPU。

## 決定性

`cargo test` 有 5 個測試：同樣輸入同樣雜湊、分段執行等於一次執行、堵住再放開物品守恆、
堵死工廠零事件，以及最重要的一個——

**懶惰結算是透明的**：每個 tick 都去讀一次全域狀態（強迫所有輸送帶結算），
最後的雜湊必須跟完全不去讀它一模一樣。這是把「懶惰 + 事件驅動」和「存檔重現 / 連線」
放在一起時最容易出錯的地方，所以從第一天就測。

狀態雜湊會先把所有懶惰狀態正規化再計算，這也正是存檔要走的路徑。

## 已知限制（還沒做的）

- 單執行緒、單一地圖分區（第 4–6 週的工作）。
- 拓撲是線性生產線，沒有分流 / 合流 / 地下帶 / 電線，機器只有一種配方。
- 測試場景的建築在記憶體裡是照生產線順序排的，真實工廠的存取局部性會更差。
- 存檔 / 讀檔還沒寫（狀態雜湊已經證明狀態可以被正規化，那是存檔的前提）。
- 試過兩個微優化都沒用：事件預取（更慢）、每 tick 把事件按 id 基數排序
  （10⁷ 時 +5%，10⁶ 時更慢，預設關閉，保留 `World::sort_events` 開關）。
